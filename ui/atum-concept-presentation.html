SLIDE 2 / 13 · INTRODUCTION & DESIGN BOUNDARIES A Atum Concept Guide

What Is Atum? What It Solves — and What It Does Not Solve

Atum creates an independent, auditable record of data completeness, consistency evidence, and dataset lineage across pipelines.

✓ What Atum Solves
Core Value Proposition
1. Verifiable Completeness & Consistency Evidence
Captures control figures (record counts, numeric totals, distinct counts, and CRC32 column hash fingerprints) at named checkpoints inside jobs.
2. Cross-System & Cross-Team Dataset Lineage
Records which datasets were produced from which (single parent, multi-parent joins, regional splits, and end-to-end flows) in one central store.
3. Instant Root-Cause Localization
Comparing control figures side-by-side pinpoints the exact job step or handoff where rows were dropped, duplicated, or altered—saving days of investigation.
4. Automated Regulatory & Audit Evidence (e.g., BCBS 239)
Replaces manual audit spreadsheet assembly with standardized evidence captured automatically on every batch run.
✕ What Atum Does NOT Solve (By Design)
Intentional Scope Boundaries
1. Does NOT Store or Move Business Data ("Privacy by Design")
Your records never leave your processing job. Atum never receives or stores PII or table rows—only aggregated control figures and descriptive labels.
2. Does NOT Intervene, Validate, or Block Pipelines
Atum does not define pass/fail rules or halt your Spark jobs when numbers shift. It records the independent evidence; your reconciliation tools and teams decide how to act.
3. Does NOT Prove Row-by-Row Immutability
Matching totals and column fingerprints are strong consistency evidence, not proof that every individual row is unchanged (e.g., swapping balances between two accounts preserves both sum and column hash).
4. Does NOT Track Individual Row-Level Lineage
Atum tracks dataset/partitioning-level lineage and aggregate figures—it does not record which specific rows contributed to a figure.

SLIDE 4 / 13 · HIGH-LEVEL ARCHITECTURE A Atum Concept Guide

High-Level Architecture: How Atum Works

Three lightweight components and a central database connect data producers with downstream reconciliation, dashboards, and audits.

Component 1
Atum Agent
Library added to a Spark job. Calculates control figures at each checkpoint and dispatches them via http, console, or in-memory capture.
Component 2
Atum Server
Central service receiving figures from all agents, enforcing lineage graph integrity, and answering queries via REST API.
Component 3
PostgreSQL Store
Central relational database holding partitionings, checkpoints, measures, lineage flows, and author audit trails in one place.
Component 4
Atum Reader
Lightweight client library for reconciliation jobs, dashboards, or audit tools to read checkpoints and flows (no Spark dependency).

SLIDE 5 / 13 · CONCEPT 1: PARTITIONING A Atum Concept Guide

Concept 1: Identifying Any Dataset Slice ("Partitioning")

Because not every system uses a data catalog or updates daily, Atum identifies datasets by an ordered key-value label.

1. Ordered Key-Value Identity (Unique Slice Label)

An ordered list of (key, value) pairs. Any two submissions with the exact same ordered keys and values resolve to the same Partitioning ID:

#1 catalog_path = edla_curated.customer_payments
#2 info_date = 2026-11-11
2. Additional Data / Partitioning Metadata (Audited Context)

Descriptive attributes attached to a dataset (such as catalog provider, join keys, app version, or owner) without changing its primary identity—every update records who made it:

catalog_provider = aws-glue
join_keys = customer_id, country_code
Example A · Mainframe Feed
Daily Mainframe Extract

Mainframe feeds do not live in Glue or Hive, so they use system, feed, and date keys:

1. system = core_banking
2. feed = payments_eod
3. info_date = 2026-11-11
Example B · Ingestion & Curation
Daily Catalog Table

Ingestion and curation apps produce tables in Glue or Hive partitioned by logical date:

1. catalog_path = raw.core_payments
2. info_date = 2026-11-11
Example C · Reference Data
Quarterly Lookup Table

Infrequently updated reference datasets use a release version instead of a daily date:

1. catalog_path = ref.iso_countries
2. ref_version = 2026-Q4

SLIDE 6 / 13 · CONCEPTS 2 & 3: CHECKPOINTS & CONTROL MEASURES A Atum Concept Guide

Concepts 2 & 3: Checkpoints & Control Measures

Checkpoints capture named milestones inside a job; Control Measures answer "Is it complete?" and "Is it unchanged?"

Sample Dataset (5 Rows × 3 Columns)
Raw Payment Transactions

Notice Row 5 (TX-105): it is a 200.00 payment, but its customer_id is null (a guest transaction).

Row Col 1: tx_id Col 2: customer_id Col 3: amount
1TX-101CUST-011,000.00
2TX-102CUST-022,500.00
3TX-103CUST-01500.00
4TX-104CUST-034,000.00
5TX-105null (guest)200.00
1. Record count — count(*) 5
Detects lost or added records at every checkpoint.
2. Financial total — sum(amount) 8,200.00
1,000 + 2,500 + 500 + 4,000 + 200 = 8,200.00 (with overflow protection).
3. Unique entities — distinctCount(customer_id) 3
3 distinct customers: CUST-01, CUST-02, CUST-03 (detects duplicate keys).
4. Column fingerprint — sumOfHashes(tx_id) #A9F4
Sums CRC32 hashes of every value in the column—changes if even one ID or string changes.
Full 8-Measure Toolkit: Also includes absSum (debits/credits), truncatedSum & absTruncatedSum (ignoring decimal rounding noise), and Provided trailer figures.

How Measures Catch Row Drops vs. Silent Amount Edits

Row counts catch missing records, but financial sums are essential to catch silent numeric corruption when row counts stay equal.

Scenario A · Row Loss or Join Filter ⚠ Measure Shift

Row 5 (TX-105, guest with customer_id = null) is dropped during an inner join with the customer master table:

tx_idcustomer_idamount
TX-101CUST-011,000.00
TX-102CUST-022,500.00
TX-103CUST-01500.00
TX-104CUST-034,000.00
TX-105null (dropped)200.00
• count(*): 5 → 4 (−1 row caught)
• sum(amount): 8,200.00 → 8,000.00 (−200.00 caught)
• distinct(customer_id): 3 → 3 (All 3 known customers retained)
• hash(tx_id): #A9F4 → #7C12 (ID fingerprint shifted)
Scenario B · Silent Amount Alteration ⚠ Measure Shift

All 5 rows arrive and all tx_id keys are intact, but Row 2's amount is corrupted from 2,500.00 to 2,050.00:

tx_idcustomer_idamount
TX-101CUST-011,000.00
TX-102CUST-022,050.00 (was 2,500.00)
TX-103CUST-01500.00
TX-104CUST-034,000.00
TX-105null200.00
• count(*): 5 → 5 (Row count completely misses this!)
• hash(tx_id): #A9F4 → #A9F4 (All 5 transaction IDs arrived!)
• distinct(customer_id): 3 → 3
• sum(amount): 8,200.00 → 7,750.00 (−450.00 caught by Sum!)

SLIDE 9 / 13 · CONCEPT 4: CROSS-SYSTEM LINEAGE & FLOWS A Atum Concept Guide

Concept 4: Linking Lineage & Flows Across Boundaries

Downstream systems reconstruct upstream Partitioning keys at the integration boundary to link Parent → Child datasets into Flows.

A Multi-Parent Joins & Splits

A dataset built from several sources links to multiple parents in one step; regional or business-unit splits create multiple child datasets from one parent.

B Built-In Graph Safeguards

Atum Server automatically rejects circular loops, prevents rewriting parent history once descendants exist, and makes re-runs with the same parents safe and idempotent.

C Optional Measure Inheritance

A newly created child partitioning can automatically inherit its parent's control measures, continuing the exact same completeness and hash checks downstream.

SLIDE 12 / 13 · ONBOARDING GUIDE A Atum Concept Guide

How to Onboard Onto Atum in 4 Lightweight Steps

Plug Atum Agent into an existing Apache Spark job (Spark 3.5 / 4.0) with a few lines of code—zero change to how your pipeline runs.

1 Add Dependency & Configure Dispatcher

Add atum-agent-spark3 (or spark4) from Maven Central and configure application.conf:

// build.sbt (Maven Central: za.co.absa.atum-service)
libraryDependencies += "za.co.absa.atum-service" %% "atum-agent-spark3" % "<ver>"
# application.conf — modes: "http" | "console" | "capture"
atum.dispatcher.type = "http"
atum.dispatcher.http.url = "http://atum-server:8080"
2 Define Partitioning & Obtain AtumContext

Define your ordered dataset keys (and optional parent partitionings to link lineage):

val partitions = AtumPartitions(List(
  "catalog_path" -> "curated.customer_payments",
  "info_date"    -> "2026-11-11"
))
implicit val ctx: AtumContext = AtumAgent.getOrCreateAtumContext(partitions)
3 Select Control Measures (Persisted Centrally)

Register measures once—or inherit them from parents. Atum remembers and restores them on future runs:

ctx.addMeasure(RecordCount())
   .addMeasure(SumOfValuesOfColumn("amount"))
   .addMeasure(DistinctRecordCount(List("customer_id")))
   .addMeasure(SumOfHashesOfColumn("tx_id"))
4 Place .createCheckpoint(...) Inline in Spark

Call createCheckpoint directly on any DataFrame at the start, between steps, and at the end:

import za.co.absa.atum.agent.AtumContext._
val rawDf = spark.read.table("raw.core_payments")
  .createCheckpoint("Catalog Input")
val joinedDf = rawDf.join(customersDf, "customer_id")
  .createCheckpoint("Joined")
3 Agent Delivery Modes: http (Server with retries & backoff), console (prints locally during dev), capture (in-memory for unit tests).
Non-Spark Systems: Onboard via direct HTTP POST to Atum Server using the interactive OpenAPI documentation at /docs/.
Reconciliation & Audit Apps: Add atum-reader (pure Java/Scala, no Spark dependency) to query checkpoints & flows.

SLIDE 13 / 13 · CONSUMPTION & AUDIT MECHANISMS A Atum Concept Guide

How Analysts & Auditors Query Lineage & History

Three core query mechanisms via Atum Reader or the REST API power discovery, flow trace, and historical trend verification.

1 Key, Property & Time-Window Discovery

Find dataset runs by any subset of partitioning keys, checkpoint properties, and a reproducible time interval [from, to):

• All tables for a business date: keys = { info_date: "2026-11-11" }
• Reproducible audit window: from = 2026-11-04T00:00Z, to = 2026-11-11T23:59Z
2 End-to-End Flow & Directional Lineage Traversal

Read all checkpoints across an entire Flow in one query, or traverse the directed graph up to N hops:

• Upstream (Ancestors): "Where did this report come from?"
• Downstream (Descendants): "Which reports depend on this raw feed?"
